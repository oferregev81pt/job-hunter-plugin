# Design: Shared CV storage across the job-hunter plugin

## Context

Six of the plugin's skills work with the candidate's CV. Five of them
(`application-packager`, `cover-letter-writer`, `fit-analyzer`, `cv-tailor`,
`interview-prep`) currently ask the user to paste their CV as a fresh input
every single time. `cv-builder` instead conversationally constructs a CV
from scratch and doesn't currently persist it anywhere. This means a user
running multiple skills in a session, or across sessions, has to re-paste
the same CV repeatedly.

The user wants the CV stored locally in the project folder and
automatically detected/reused on subsequent runs, instead of asking to
paste it every time.

This reuses the local-storage convention already established by
`notion-connector`'s local-file mode (`./job-search-tracker/`), so all
local job-search state lives in one place rather than introducing a second
storage location or a new skill.

## Change

### Storage location
`./job-search-tracker/cv.md` — plain markdown, the CV content exactly as
pasted (or as generated by `cv-builder`), no reformatting on save.

### Check-then-load-or-save flow (added to 5 skills)

Replace each skill's "Please paste your CV" input step with:

1. Check whether `./job-search-tracker/cv.md` exists and is non-empty.
2. **If found:** tell the user "Found your saved CV — using it." and use its
   contents directly. Do not ask the user to paste anything. Move on to the
   next input.
3. **If not found (missing, empty, or unreadable):** ask the user to paste
   their CV as today. Once provided, save it verbatim to
   `./job-search-tracker/cv.md` (creating the `job-search-tracker/` folder
   first if it doesn't exist) before proceeding with the rest of the skill.
4. **If the user pastes a CV unprompted when a saved one already exists**
   (e.g. "here's an updated version, use this instead"): overwrite
   `cv.md` with the new content immediately, no confirmation needed, then
   proceed.

### `cv-builder` integration

After `cv-builder` finishes generating the final CV and presents it to the
user as it does today, additionally save that same final CV verbatim to
`./job-search-tracker/cv.md` (creating the folder if needed), so it becomes
available as the shared source CV for the other five skills. This is an
addition to `cv-builder`'s existing output — it does not change what's shown
to the user, only that a copy is now also persisted.

### What is explicitly NOT cached

- **Job descriptions.** Always fresh per skill run — no JD caching.
- **`cv-tailor`'s tailored output.** The tailored CV `cv-tailor` produces is
  role-specific and must never overwrite `cv.md`. Only the original CV
  provided as *input* (via paste, or previously saved) is ever written to
  `cv.md`. `cv-builder` is the one exception, since generating a canonical
  CV is its entire purpose.

### Edge cases
- `cv.md` exists but is empty, whitespace-only, or otherwise clearly not a
  CV (e.g. unreadable): treat as "not found" and fall back to asking for a
  paste, then overwrite with the new content per the normal save step.
- The `job-search-tracker/` folder may already exist from `notion-connector`
  local mode, or may not exist yet — either way, create it if missing rather
  than erroring.

## Non-goals
- No new skill or shared "cv-connector" component — the check-then-load-or-save
  instructions are written directly into each of the 5 consuming skills
  (and the save step into `cv-builder`), consistent with how each skill
  today already duplicates its own "paste your CV" step rather than sharing
  one.
- No versioning or history of prior CVs — `cv.md` always holds only the
  latest version; overwriting is silent and immediate per the earlier
  design decision.
- No confirmation prompt before overwriting `cv.md` with a newly pasted
  CV — this was explicitly decided against in favor of always using the
  latest paste.

## Testing / validation approach

Prompt-only change, no automated tests. Validate manually: run any of the
5 CV-consuming skills with no `cv.md` present — confirm it asks to paste,
then confirm the file is created with the exact pasted content. Run the
same skill again — confirm it finds and uses the saved CV without asking.
Run `cv-builder` end-to-end and confirm its final output is saved to the
same file. Paste a new CV unprompted in a later run and confirm the file is
overwritten with the new content.
